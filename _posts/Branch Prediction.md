### 0x00. Intro 
 
분기예측은 어떻게 이뤄지는가?
 
 > 분기 예측(Branch Prediction)은 CPU가 실행경로를 미리 예측하는 기술이다
 
### 0x01. Branch Patterns
현대 CPU는 작업이 전환될때 끝과 시작 명령을 *거의* 동시에 실행한다. 즉, 어떤 작업이 끝나기도전에 다른 작업이 수행된다. 분기문도 마찬가지로 조건이 확정되기전에 명령어를 실행하는데, 이때 분기 예측을 사용한다.
간단한 반복문으로 살펴보자. 

``` 
## branch_A.c
int idx = 0;
while (idx < 100) idx++;
```

``` 
## branch_A.asm
mov eax, 0        ; idx = 0

LOOP:
cmp eax, 100      ; idx < 100 ?
jge END           ; idx >= 100이면 종료

add eax, 1        ; idx++
jmp LOOP          ; 다시 조건 검사

END:

```

idx 값을 보라. idx값이 계속 증가하면서 조건문의 True 상태가 반복적으로 나올것이다. 이러한 상태가 반복되면 어느 시점부터 분기예측이 이뤄진다. 그 결과 cpu는 연산을 미리 실행하고, 상태값을 기록해둔다.
분기 예측은 일관성이다. 동일한 결과가 여러번 나오거나 데이터가 연속성을 가질 경우 분기 패턴을 가지게 된다.
당연히 분기 예측은 100%가 아니다. 다른 코드를 보자.

``` 
## branch_B_1.c
// 1-100 까지 무작위 원소
int values[100] = {1,5,53,10,12,77,85, ...} 
int count = 0;
// 1일 때만 증가
for (int i = 0; i < 100; i++) {
	if (values[i] == 1 ) count++; 
}
```

배열 안의 원소들은 무작위로 배치되어있다. 1이 아닌 경우가 반복되면, cpu는 다음분기를 거짓으로 예측한다.
<br>

배열  : 1  5  3  10  12  77  85 ... <br>
조건문: T  F  F  F    F   F   F ...

이 코드에서 조건만 살짝 바꿔보면 어떨까?

``` 
## branch_B_2.c
int values[100] = {1,5,53,10,12,77,85, ...} 
int count = 0;
for (int i = 0; i < 100; i++) {
	// 50 이하면 증가 
	if (values[i] <= 50 ) count++; 
}
```

조건 결과에 일관성이 없다. cpu는 예측을 하더라도, 눈 감고 찍는것과 진배없다. 왜냐하면 50이하의 숫자는 여러 조합이 가능해 특정 규칙을 만들어낼 수 없다.

배열   :  1  5  53  10  12  77  85 ... <br>
조건문:  T  T  F    T    T    F   F ...

중요한건 조건이 판정되고나서다. 입력 데이터와 조건식의 형태에 따라 분기예측률이 달라진다. cpu는 컴파일과 런타임 모든 환경에서 분기 결과에 대한 판정과 학습을 한다. 
지금까지 대략적인 분기 예측 과정을 살펴봤다. 이제 컴퓨터를 괴롭힐 시간이다.


### 0x02. Branch Mark

아래는 실행 환경과 테스트 코드다.

| Category   | Description              |
| ---------- | ------------------------ |
| Hw         | M1 Pro                   |
| Os         | macOS 15.6               |
| Tools      | simple-kpc               |
| Input Data | Random, Sorted Data(0,1) |
| Metrics    | Execution Time           |

```
//Branch_mark.c
#define N 100'000'000 
unsigned char random_data[N];
unsigned char sorted_data[N];

long count_ones(const unsigned char *values) {
	long sum = 0;
	for (int i = 0; i < N; i++) 
		if (values[i]) sum++;
	
	return sum;
}
```

위 코드는 1억개의 원소중에 1의 갯수를 세는 함수다. 인자로 0과1로 이뤄진 배열을 받는다. 이 배열은 두 종류로 나뉜다. 정렬 상태와 무작위 상태로 분기 예측률을 명확히 나누기 위함이다. 
그렇다면 실제 테스트 결과는 어떨까? 


![컴파일 최적화 없이 측정한 분기 예측 결과]({{ '/assets/images/branch-prediction/unoptimized.png' | relative_url }}){: width="461"}

<b>컴파일 최적화 비활성</b>

데이터(배열)별로 100회씩 실험 했고, 그중 유의미한 데이터를 70개 선별했다. 
우리의 관심사는 분기 패턴이다. 정렬된 원소의 예측률은 100%에 가까운 반면 무작위 원소는 50%를 겨우 넘었다. 가설과 거의 일치한다. 분기 예측을 실패하면 연산횟수가 늘어나므로 당연히 실행시간에서도 차이가 난다.
그러나 컴파일 최적화를 하게되면 이야기가 달라진다. 
동일한 코드에 최적화 명령어를 사용해 컴파일을 하고 실행시간을 측정했다. 

![컴파일 최적화 여부에 따른 실행시간 비교]({{ '/assets/images/branch-prediction/optimization-comparison.png' | relative_url }}){: width="523"}

**컴파일 최적화 X `-O0` vs 컴파일 최적화 O `-O2`**

흥미로운 결과가 나왔다! 컴파일 최적화를 하면 두 데이터 모두 비슷한 성능을 보여준다. 
특히 무작위 데이터는 34배에 달하는 성능 향상을 보여준다. 어셈블리를 확인해보니 점프가 사라졌다. 컴파일러가 무슨 마법을 부린걸까? <br>
원소 한개씩 확인하지않고 여러개의 원소를 그룹으로 묶어서 한꺼번에 연산하는 아이디어다. 
예시로, 원소가 1  5  2  3  20  1  77  1  인 배열이 있다. 그룹 하나당 원소 4개로 묶는다. 이때 조건에 통과한 원소만 1로 할당하면 아래와 같은 그룹이 만들어진다. 

> 그룹1 : 1 0 0 0  
> 그룹2 : 0 1 0 1

이후 분할된 그룹끼리 누계를 구해주면 1의 갯수가 나오게된다. 컴파일러가 분기를 제거함으로써 성능 최적화를 수행한다. 주의해야할것은 시간복잡도는 똑같다. 데이터 처리량을 늘린거지, 검증하는 원소 갯수는 동일하기 때문이다. 

### 0x03. Outro
지금까지의 메세지는 분명하다. 분기예측은 성능에 영향을 준다. 여전히 분기 예측은 지상 과제다. 애플과 인텔과 같은 제조사들도 정확도를 95% 이상 달성하고자 다양한 패턴을 학습한다. 또한 분기 테이블이라는 자료구조를 통해 분기 예측률을 높인다. 
분기예측도 결국 비용이다. cpu가 많은 인스트럭션을 처리하기위해 불확정성을 제거한것이다. 어셈블리같은 저수준은 컴파일러에게 맡길수밖에 없다. 그럼에도 고수준 단계에서도 병목은 상존한다. 가장 필요한건 관심이다.
